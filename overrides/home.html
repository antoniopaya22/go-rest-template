Go REST API template

Start from a service,
not a skeleton.

A working Go API with an enforced OpenAPI contract, token authentication and two databases, plus a tool that renames it and removes the parts you do not want.

Get started View on GitHub ↗
  • Go 1.26+ chi router, log/slog, database/sql; no framework
  • OpenAPI 3.1 embedded in the binary and checked on every request
  • PostgreSQL and SQLite served by one repository implementation
  • MIT licensed
What you getA service that already runs
What you chooseDatabase, modules, deployment
What you keepOnly the code you chose

The problem

The same decisions,
every new service.

Before a new API does anything useful it needs an error format, pagination, authentication, migrations, configuration, logging, tests and a way to ship. A template answers those once. A template you cannot trim leaves code in your repository that you did not choose and have to maintain.

Decided, not implied

Errors, lists, concurrent updates and tokens each follow one documented convention, used by every endpoint.

Removable by design

Optional code is delimited by marker comments. Turning a module off deletes it together with its dependencies.

Checked, not promised

CI generates projects with different options and builds, vets and tests each one.

How it is organised

Features on top,
platform below.

A feature package owns its model, rules, storage and HTTP endpoints. The platform layer holds what features share. One file, the composition root, knows about all of them.

01

Feature packages

internal/users and internal/tasks each hold a model, a service, a repository and a handler. Features do not import each other.

02

The contract decides

api/openapi.yaml is embedded in the binary. Requests that do not match it are rejected, and a test fails when a route and the document disagree.

03

One composition root

internal/app constructs every component and mounts every route. Adding a feature touches two files there and nothing else.

project layout
api/openapi.yaml        # the contract, embedded and enforced
cmd/api                 # the server
cmd/migrate             # up, down, status
internal/
  app/                  # composition root: wiring and routes
  auth/                 # tokens, passwords, authentication middleware
  users/                # a feature: model, service, repository, handler
  tasks/                # the example feature, source of the generator
  config/               # every variable declared once
  platform/             # database, httpx, middleware, contract, tracing
migrations/             # SQL per driver, embedded
tools/init              # turns the template into your project
tools/scaffold          # generates a resource

Make it yours

Keep what you need,
delete the rest.

The init tool renames the module and the application, removes the options you turn off, deletes what belongs to the template itself, runs go mod tidy and regenerates the example environment file. It asks questions, or takes flags.

terminal
$ go run ./tools/init -yes \
    -module github.com/acme/billing -db postgres -tracing=false
billing is ready.

  module   github.com/acme/billing
  kept     dev container, example resource, helm chart,
           metrics, postgres, rate limiting
  removed  observability stack, sqlite, tracing
$ make check
internal/app/routes.go
r.Use(middleware.Logger(a.logger))
r.Use(middleware.Recover)
// init:metrics:begin
if a.cfg.Metrics.Enabled {
    r.Use(middleware.Metrics(a.registry))
}
// init:metrics:end
r.Use(middleware.SecurityHeaders)

a.users.Routes(r, a.authn)
a.tasks.Routes(r, a.authn) // init:example

make test-init, which CI runs, generates nine projects with different options. Each one must be free of template leftovers, pass gofmt, build, pass go vet and pass its tests; projects that keep the example also generate a resource and test it. What is in the box

The parts you would
write anyway.

Each item is implemented, tested and documented. The ones marked optional can be removed when you create your project.

Problem responses

RFC 9457 errors with a stable code, the request ID and per-field details. Internal causes are logged, never sent.

Cursor pagination

Lists return {data, next_cursor} with an opaque cursor, 20 items by default and 100 at most.

ETag and If-Match

Every row has a version. A stale If-Match gets 412 and a concurrent write gets 409.

Rotating refresh tokens

Each refresh token works once. Presenting it twice revokes every token issued from that login.

HS256 or EdDSA

With EdDSA the public key is published at /.well-known/jwks.json.

Migrations

Embedded SQL run by goose, with down migrations and an advisory lock on PostgreSQL.

Admin port

Metrics and pprof listen on a separate port, away from the public API.

Prometheus metrics

Request count, latency histogram and in-flight gauge, labelled by route template. Optional.

OpenTelemetry

Server spans exported over OTLP/HTTP when OTEL_ENABLED=true. Optional.

Rate limiting

Per client IP, with a tighter budget for the authentication endpoints. Counters are per process. Optional.

Helm chart

Probes, restricted security context, and optional ingress, autoscaling, disruption budget and network policy.

Release automation

release-please cuts versions; binaries ship with an SBOM and the image is signed with cosign.

Questions.

Why chi and not a framework?

chi is a router built on net/http: handlers are standard http.HandlerFunc values and middleware is func(http.Handler) http.Handler. Nothing in the feature packages depends on a framework type, so the router is the only part you would have to replace.

Why hand-written SQL instead of an ORM or a generator?

The template supports two databases with one repository per resource. Queries are written once with ? placeholders and rewritten for PostgreSQL at run time, which keeps the SQL visible and the generator simple. If you keep a single database, adding a query generator is a local change inside each repository.

Why two binaries?

cmd/api serves and cmd/migrate changes the schema. Keeping them apart lets you run migrations as a separate step with different credentials. Both are in the container image, and the server can also migrate at startup with DATABASE_AUTO_MIGRATE.

Is SQLite supported in production?

It works, with limits: the pool is one connection because SQLite has a single writer, and the Compose file and the Helm chart assume PostgreSQL. SQLite is meant for development, tests and small single-instance deployments. PostgreSQL is the production default.

How do I pick up later changes of the template?

There is no automatic sync. A generated project is independent: the init tool deletes itself and the markers, and from then on the code is yours. To adopt a later change, read the changelog and port what you want.

What does the init tool do with the license?

It keeps LICENSE, which is the MIT license of the template. Add your own copyright line or replace the file with the license of your project.
